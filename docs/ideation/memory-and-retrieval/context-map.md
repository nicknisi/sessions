### Edge Cases

- A pi fixture filename containing `_` loses everything before the last underscore: `src/session-id.ts:28-31` splits on it. Claude fixtures are safe because the in-file `sessionId` wins (`session-id.ts:24`) — but only if you set it, and it must equal the basename or `queries.ts` `expect` entries silently never match.
- A fixture with no resolvable `cwd`, or a `cwd` containing `.claude/worktrees` or `/.bare`, is ignored at `src/cache.ts:402-403` and shows up only as a `CORPUS_SIZE` mismatch.
- An empty or unparseable transcript lands in `ignored_files` (`cache.ts:384-396`) with the same silent-shrink effect.
- Ties: `merged.sort` (`cache.ts:899`) breaks equal `finalRank` on `date` descending, so two fixtures with identical relevance are ordered by timestamp — give new fixtures deliberate, distinct ISO timestamps.
- A new fixture under a junk cwd prefix is invisible to every unscoped query (`cache.ts:761`, `wrapped/exclude.ts:27-30`).
- Adding a fixture that matches a *negative* query's vocabulary changes `NEGATIVE_RESULTS` (`eval.test.ts:45-51`), which is an exact `toEqual`, not a bound. Three of the five already return a full page of 5.
- Adding documents changes `median chars`/`max chars` per class, so `PAYLOAD_CEILING` moves even when recall does not — this is exactly how two of the four mutants "die" today.
- `structuredClone(RANKING)` deep-copies the `sessionRank` array, so `Object.assign(RANKING, saved)` restores it correctly; a shallow `{...RANKING}` would not if a mutant mutated the array in place rather than replacing it.
- Mutating `RANKING.sessionRank` changes the interpolated SQL text, so Bun's per-`Database` prepared-statement cache prepares a new statement — and since `runEval()` opens a fresh DB each call, there is no cross-run statement staleness.
- `runEval()`'s env restore uses `delete process.env[k]` when a key was previously `undefined` (`run.ts:201`). Under `bun test` the preload has set all five, so nothing is deleted — but under `bun run eval` on a bare shell it does delete, which is correct there.

### Risks

- **The spec's central premise understates the work by 2×, and I measured it.** The spec and `contract.md:19` both say the corpus "is insensitive to two of the four" mutants. Measured against the recall ratchet, **all four survive** — no `RECALL_FLOOR` entry is violated by any mutant, and not one expected-answer rank degrades. Expect four survivors on the first harness run, not two, and budget the fixture work accordingly. This is a decision-log contradiction: the entry _"Retrieval quality becomes a real track, with corpus growth as its prerequisite"_ and the entry _"The corpus is done when four named mutants are killed"_ both rest on the two-of-four premise; the premise is wrong in the direction that makes the phase *more* necessary, so the decisions stand, but the effort estimate does not.
- **Two mutants "die" today for the wrong reason, and the spec's `anyFloorViolated` will believe them.** `USER_HIT_BOOST → 1.0` exceeds two payload ceilings (exact-error-string 5847 vs 5826, command 4393 vs 4352) and `finalRank → best-of` exceeds one (multi-word 6592 vs 6506) — deltas of 21, 41 and 86 characters, incidental serialization wobble with no ranking meaning. If `anyFloorViolated(report)` reuses *all* of `eval.test.ts`'s assertions it will report 2/4 killed on day one and 4/4 after the first two fixtures, while the corpus is still blind. **`anyFloorViolated` must compare `RECALL_FLOOR` only.** Note the corollary: re-recording the ceilings in step 3.4 can silently *un*-kill those two mutants, so re-run the harness after re-recording, not before.
- **The killing oracle is one-sided and two mutants move the metric the wrong way.** `bm25`-flat and `USER_HIT_BOOST → 1.0` both promote `nl-webhook-signature-fix` from rank 2 to rank 1, lifting multi-word recall@1 from 0.80 to 1.00. A "did a floor drop?" test can never see an improvement, so today's tuned constants are actively *hurting* that query and the harness would call the mutant a survivor forever. New fixtures for these two mutants must create a case where the tuned value is strictly better, not merely different — and it is worth asking whether `nl-webhook-signature-fix`'s recorded miss is itself a mis-tuning rather than a distractor working as designed.
- **The spec's harness snippet never awaits the eval, which makes it vacuously green.** `runEval()` is `async`; the snippet's `if (!anyFloorViolated(runEval())) survivors.push(...)` passes a `Promise` into the comparison. Depending on how `anyFloorViolated` destructures, that is either a crash or — worse — a truthy object that reports every mutant killed. The test callback must be `async` and each call `await`ed. This is precisely the "vacuously green" failure the inventory assertion exists to prevent, reintroduced two lines below it.
- **`RECALL_FLOOR` lives inside a test file and importing it duplicates a whole suite.** It is module-private at `eval.test.ts:21`. I verified the consequence: a `b.test.ts` importing from `a.test.ts` reports "2 tests across 1 file" — the imported file's tests re-register in the importing file and run again, including its `beforeAll`. There is no test-imports-test precedent anywhere in this repo. Move `RECALL_FLOOR`, `PAYLOAD_CEILING` and the comparison into a non-test module (`src/eval/floors.ts`, or export them from `run.ts`) and have both test files import from there. The spec's Modified Files table does not anticipate this file.
- **`bun test` runs all 44 files in one process, so an unrestored `RANKING` poisons other files.** Verified: two test files reported the same `process.pid` and shared a module instance, and the execution order was not alphabetical (`b.test.ts` ran before `a.test.ts`). A mutation that escapes the `finally` — a throw inside `anyFloorViolated`, or an `expect` inside the loop — leaves `cache.search.test.ts:816` and `eval.test.ts` scoring against flattened weights. Keep the `finally`, and add an `afterAll` that re-asserts the defaults as a belt.
- **`finalRankMode: 'best'` is new production behavior, not a hoist.** `searchSessions` has no best-of branch today; the record's fifth field requires adding a `Math.min` arm at `cache.ts:896` that ships to users and is exercised only by a mutant. The spec's "No behavior change: the defaults are exactly today's values, verified by the eval baseline staying byte-identical" is true of the default arm only — the byte-identical check cannot validate the new branch at all. Decide deliberately whether an unreachable-in-production code path is worth the mutant, and if so, give it a comment saying so.
- **`NEGATIVE_RESULTS` (`eval.test.ts:45-51`) is an exact-equality characterization the spec's re-record list omits.** So are the narrative comments at `eval.test.ts:15-20` (which explains the floors in terms of s21) and `:29-31` (which explains the ceilings in terms of a field rename). Growing the corpus invalidates all three; the spec mentions only `RECALL_FLOOR` and the ceilings.
- **Every line reference in the spec and the contract is stale by ~117 lines.** Phase 1 inserted the refresh-marker block into `cache.ts`, so the spec's `:666 / :707 / :713-714 / :758` are now `:783 / :824 / :830-831 / :896`, and `contract.md:19`'s `cache.ts:779` (the finalRank FOLLOW-UP) is now `:880`. Do not trust a spec line number in this file without re-locating it.
- **Nothing in CI enforces the baseline.** `.github/workflows/ci.yml` has no eval job, so `docs/eval-baseline.md` can silently rot; only the floors and ceilings inside `eval.test.ts` are protected. If the intent is a ratchet, the diff belongs in CI — out of scope for this spec, but worth naming in Open Items rather than assuming it is covered.
- **The "slow harness" failure mode does not exist.** Measured: the entire `eval.test.ts` file (17 tests, one full `runEval`) runs in 71ms, and `bun test` end to end is 3.72s. Five `runEval()` calls cost roughly 0.4s. The spec's "if it exceeds ~10s, scope to a subset of classes" mitigation should not be allowed to justify cutting corpus coverage.
- **`bun run eval` is not covered by the test preload.** `bunfig.toml`'s `[test] preload` applies to `bun test` only; `run.ts:163-177` redirects five vars itself and does **not** set `SESSIONS_MEMORY_DB` or `SESSIONS_HOME`. Harmless today because `searchSessions` never touches the memory store — but if anything on the eval path ever reaches it, `bun run eval` writes to the operator's real `~/.local/share/sessions/memory.db`, and phase 1's `assertNotRealStore` will not stop it (it only fires when `SESSIONS_TEST` is set).
- **`src/cache.ts` is claimed by phase 4 as well** (`contract.md:173` — a three-way collision across phases 1, 3 and 4). The hoist should land and be merged before phase 4's refresh-bypass edits begin.
- **Overfitting is the real hazard here, and the current corpus proves why.** Zero of 26 queries change rank under any of the four mutants: every existing answer wins by a margin far wider than any constant can close. Fixtures that create near-ties are the only thing that will move the harness — and a near-tie authored to be exactly sensitive to one constant is, by construction, close to the "probe, not a plausible session" failure the spec warns about. The `competes` field on each new query is the place to make the distractor's plausibility legible.

### Conventions

- **Naming**: flat `src/*.ts`, lowercase, dot-suffixed test files next to their subject (`memory.ts` → `memory.test.ts`, `memory.survival.test.ts`, `memory.export.test.ts`). Fixtures in `src/__fixtures__/`. Module-private helpers are plain `function`; the exported surface is explicit. Constants are SCREAMING_SNAKE at module scope (`SCHEMA_VERSION`, `LESSON_MAX_CHARS`, `SAME_LESSON_JACCARD`).
- **Imports**: relative with no extension (`./paths`, `../cache`), no barrels. `verbatimModuleSyntax` is on, so type-only imports must be written `import type`. `node:` prefix on all builtins (`node:fs`, `node:path`, `node:os`). `bun:sqlite` / `bun:test` for Bun builtins. One in-file `require('node:fs')` exists at `src/cache.ts:84,198,290` — legacy, not the pattern to copy.
- **Error handling**: swallow-and-continue for anything disposable (`try {} catch {}` around unlinks and readdirs); throw only where the caller can act. Failures the user must know about are written to `process.stderr` and never to stdout (stdout is a data channel — see `src/stdout.ts`). `isCorruption()` exists twice on purpose (`src/cache.ts:206`, `src/memory.ts:162`) with opposite responses — delete-and-rebuild vs quarantine-and-keep.
- **Types**: `interface` for object shapes, `type` for unions/aliases; `LessonRow` mirrors the SQL columns in snake_case while the exported projection (`ExportedLesson`) is camelCase. `db.query<Row, Params>()` is always parameterized. `strict` + `noUncheckedIndexedAccess` are on, so indexed access needs `!` or a guard.
- **Testing**: `bun:test` with `describe`/`test`/`expect`; `spyOn(process.stderr, 'write').mockImplementation(...)` is the only mocking idiom in the repo (10 uses) — there is no `mock.module` anywhere. Hermetic files use `mkdtempSync(join(tmpdir(), 'sessions-<area>-'))` at module scope, set env, then `await import(...)` the subject. Real subprocesses are preferred over simulated races. Test prose is explanatory (a `describe` name is a sentence).
- **Formatting**: `.oxfmtrc.json` — single quotes, semicolons, trailing commas everywhere, 2-space indent, printWidth 120. `oxlint` runs with an empty rule set, so `bun run format:check` is the real style gate. `ignorePatterns` covers `dist/`, `node_modules/`, `CHANGELOG.md`, `.github/`, `plugin/*/plugin.json`, `docs/ideation/` — note `docs/` generally is **not** ignored.

### Risks

- **`PRAGMA data_version` cannot order the snapshots as the spec uses it — verified, two separate defects.** (1) The column is named `data_version`, so the spec's `db.query<{n:number}>('PRAGMA data_version').get()?.n ?? 0` evaluates to `0` on every call and the `gen >= readSnapshotGeneration()` check silently degrades to `0 >= 0` — always true, guard absent. (2) SQLite does not increment `data_version` for changes made on the *querying* connection; measured directly: after this connection's own `INSERT` it stayed `1`, and only a second connection's commit moved it to `2`. So the writer that just committed sees a counter that does not reflect its own write, which is exactly the ordering the contract criterion depends on ("the surviving snapshot contains the LATEST committed rows"). A monotonic counter bumped inside the same transaction as the lesson write (or `MAX(id)`+`MAX(last_seen_at)` read post-commit) is needed instead. Do not ship the spec's snippet verbatim.
- **"The lock is an atomic `mkdir` (the repo's existing idiom)" is false — there is no such idiom.** Every `mkdirSync` in the tree passes `{recursive: true}`, which never throws `EEXIST` and therefore cannot function as a lock. The repo's real cross-process idiom is atomic tmp-write + `renameSync` (`src/report/pricing-cache.ts:63-74`). The mkdir lock must be written from scratch, including the dead-PID reaping the spec asks for, and a leftover lock *directory* beside `memory.db` will break `src/memory.test.ts:54`, whose `beforeEach` does `for (const f of readdirSync(fixtureRoot)) unlinkSync(...)` — `unlinkSync` on a directory throws `EPERM`/`EISDIR`.
- **`src/memory.survival.test.ts:84-100` deletes all eight `SESSIONS_*` vars in `afterAll`.** This is the live hermeticity hole and it is in-scope even though the spec's Modified Files table omits it: after that file runs, any later test file in the same process resolves the **real** `~/.local/share/sessions/memory.db` and `~/.cache/sessions/index.db`. Once `assertNotRealStore` lands, this teardown turns the suite red rather than silently corrupting the store — good, but the builder must restore the preload's values instead of deleting. Same class, lower stakes: `src/report/pricing-cache.test.ts:16` and `src/report/extract.test.ts:76-78` also `delete` overrides.
- **A new `meta` table will survive a `SCHEMA_VERSION` bump unless it is added to the drop list at `src/cache.ts:120-123`.** That list is hardcoded, not schema-driven. Leave `meta` out of it and a version bump empties every index table while `last_refresh_ms` still reads "just walked" — `ensureIndexFresh` then skips the rebuild and serves an empty index for the length of the refresh interval (longer if `SESSIONS_REFRESH_INTERVAL_MS` is raised).
- **`--purge-lessons` stops purging.** `purgeLessons()` (`src/memory.ts:979-989`) removes only `memory.db` and its journal sidecars. After this phase, `memory.db.snapshot` and `lessons.jsonl` — a byte-complete copy and a plaintext dump of the same lessons — survive a purge the user was warned costs them "N lessons that nothing can regenerate" (`src/setup.ts:344`). `src/memory.survival.test.ts:211` still passes because it only asserts `memory.db` is gone, so nothing catches this. Extend `purgeLessons` and its test.
- **Both seams the spec's experiments need are module-private.** `discoverFiles` (`src/cache.ts:231`) is not exported and cannot be stubbed — there is no `mock.module` usage in the repo, and it internally swallows `readdir` failures (`:241, :257`), so it is hard to make throw at all. `ensureIndexFresh` (`:541`) is not exported either, so `src/__fixtures__/concurrent-refresh.ts` cannot call it directly; the child must go through an exported consumer (`searchSessions`, `getIndexDb`, `getContextPrimer`) or the builder must add an explicit test seam. Also note `refreshIndex` does **not** consult the marker in the spec's design — only `ensureIndexFresh` does — so a fixture calling `refreshIndex` will always walk.
- **The marker makes `ensureIndexFresh` return a stale `{total: 0, updated: 0}`.** A fresh process that skips the walk on a marker hit returns the module-initial `_lastRefreshResult` (`src/cache.ts:68`), i.e. "0 sessions indexed". No current consumer reads that value (`src/eval/run.ts:181` calls `refreshIndex` directly), but any future "indexed N" display would be lied to. Also, `closeDb()` (`:102`) resets `_lastRefreshAt = 0`, which wipes an in-process failure backoff — the backoff test must not call `closeDb` between attempts.
- **`_lastRefreshAt = Date.now() - refreshIntervalMs() + FAILURE_BACKOFF_MS` back-dates into the future when the backoff exceeds the interval.** With the 5s default and a 30s backoff, `_lastRefreshAt` lands 25s ahead of now. The comparison still behaves, but it also overrides an explicit `SESSIONS_REFRESH_INTERVAL_MS=0` ("always refresh") with a 30s lockout, and a future-dated `_lastRefreshAt` is the same shape as the clock-skew failure mode the spec's own table says to treat as expired.
- **Three paths bypass `paths.ts` and the preload cannot reach them.** `src/opencode.ts:17` resolves `SESSIONS_OPENCODE_DB` against a raw `homedir()`, not `getHome()` — so with only the spec's five vars set, every index refresh under test reads the developer's real OpenCode database (this is why `src/cache.search.test.ts:22` and `src/memory.survival.test.ts:29` set it by hand). `src/hooks.ts:36` does the same with `SESSIONS_CLAUDE_CONFIG_DIR`, and that one is a *write* path into `~/.claude/settings.json`. `src/scanner.ts:12-15` freezes `homedir()` at import and honors no override at all; it is reachable (`index.ts:5`). Reads cannot fail the contract's byte-identical check, but the hooks write can — add `SESSIONS_OPENCODE_DB`, `SESSIONS_CLAUDE_CONFIG_DIR`, and the three source-root vars to the preload.
- **The guard only covers DB openers, so a scrubbed-env child that does anything else is still unprotected**, by design. Related: `src/mcp.test.ts:376` spawns the real MCP server with no `env` at all (inheriting, therefore safe under the preload), while `:488`, `:537`, `:598` and `src/trajectory.test.ts:162` spawn with `{...process.env, <override>}` — also safe. The spec's `env: {}` experiment is synthetic; on macOS a child with a truly empty environment still starts because `process.execPath` is absolute, but keep `stderr: 'pipe'` and assert on the message, not just the exit code.
- **Spec claims verified as accurate** (no action needed, recorded so a later phase does not re-derive them): exactly 11 of 41 test files reference `SESSIONS_MEMORY_DB`/`SESSIONS_CACHE_DIR` across exactly 42 occurrences; `bunfig.toml` does not exist yet; `VACUUM INTO` works in Bun's SQLite and accepts a bound parameter (`db.run('VACUUM INTO ?', [path])`), so the spec's manual quote-escaping is unnecessary; the `SESSIONS_DIFFERENTIAL=1` opt-in suite at `src/record.test.ts:232-238` reads `homedir()` directly and is therefore *not* broken by a `SESSIONS_HOME` redirect.
