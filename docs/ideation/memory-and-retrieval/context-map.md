### Conventions (delta from the prior maps, which still hold)

- **Machine surfaces**: stdout is the data channel and stderr carries everything else (`src/stdout.ts`; `context.ts:253` writes `wrote <path>` to stderr, `index.ts:116,130` writes the spinner and the empty-result notice to stderr). Non-pretty `JSON.stringify` on MCP paths (`mcp.ts:53, 315`); pretty-printed only where a human reads it (`lessons.ts` export).
- **Exit codes today**: every `die()` in the tree exits 1 (`cli.ts:76`, `context.ts:26`, `distill.ts`, `trajectory.ts`, `report/index.ts`, `wrapped/index.ts`); `usage()`/`help()` exits 0. There is no exit-2 precedent anywhere — grep-style codes are a new convention this phase introduces.
- **Subcommand shape** (unchanged from the Phase 2 map): the feature module owns `parse<X>Args` + `run<X>`; `index.ts` dispatches on `Bun.argv[2]` with a dynamic import and `process.exit(0)`; `src/cli.ts` owns only the root search parser and the usage text. `search` is the exception the spec creates — it is the root parser's own command, so `parseSearchArgs` genuinely belongs in `cli.ts`.
- **Test spawns**: always `env: { ...process.env, <overrides> }`. Never bare `Bun.spawn` without `env` — measured again on Bun 1.3.14, the child gets the environment as of *process start*, so it sees neither the preload's `SESSIONS_*` redirection nor `SESSIONS_TEST`, and `assertNotRealStore` cannot fire for it.

### Edge Cases

- **A cold cache under `--no-refresh`.** `getDb()` runs before `ensureIndexFresh()` in both `searchSessions` (`:748`) and `getContextPrimer` (`:1349`), so the index file is created regardless. The flag has to gate the *open*, not just the walk — e.g. `if (noRefresh && !existsSync(getDbPath())) return <empty>` before `getDb()` (`existsSync` is already imported in `cache.ts`). The spec's own key decision ("against an empty cache dir it must build **no index at all** … because a flag that is parsed and ignored would otherwise pass") is the criterion that fails.
- **A stale-but-present index under `--no-refresh`** must return whatever is there, not error — that is the spec's stated intent and it falls out for free once the open is gated on existence.
- **Zero results with `--json`** — emit the envelope with `results: []` *and* exit 1. Exit-code-only is not enough: contract criterion 45 pipes stdout into a JSON parser under `pipefail`.
- **A large result set on a pipe** — `writeStdoutFully` must be `await`ed before `process.exit`. Measured truncation at exactly 65,536 bytes otherwise, and the CLI's default limit is 1000 results at ~1.1 KB each.
- **`-v`, `--version`, `--clear-cache`, `--mcp` inside a search query.** All four are matched with `Bun.argv.includes(...)` anywhere in argv. Measured: `search --json -v` prints `sessions 1.15.3` and exits 0; `search --json --clear-cache` wipes the index and exits 0. A script passing an untrusted term gets non-JSON on stdout with a success code, or loses its cache.
- **`sessions search` as a query.** Quoting does not help — the mitigation in the spec's Failure Modes table is wrong. If the word must remain searchable, the real escape hatches are `sessions -- search`, `sessions search search`, or `sessions --query search`; pick one and document *that*.
- **`context --json` outside a git repo.** `runContext:236-239` writes `Not inside a git repository.` to stderr and exits 0 with **empty stdout** — a statusline calling `JSON.parse('')` throws. A JSON surface needs either an envelope with an empty/`null` primer or a distinct exit code.
- **`context --json --out <path>`** — `runContext:250-259` branches on `args.out`. Decide whether `--json` writes the JSON to the file or the flags are mutually exclusive; silently ignoring one of them is the trap.
- **`context --json --hook`** — `runContext:230-233` returns through `runContextHook`, which appends a prose pointer paragraph (`:341-343`) and swallows every error. `--json` must either reject the combination or bypass hook mode; emitting markdown prose after JSON is the failure.
- **`--no-refresh` inside the refresh interval is a no-op**, because phase 1's marker already skipped the walk (measured: five consecutive warm `context` runs, zero walks). Any timing-based test of the flag will show no difference; assert on `refreshAttempts()` or on the absence of `index.db`, never on elapsed ms.
- **Two spawns sharing one temp cache dir** — the marker lives *in* `index.db` (`cache.ts:637-642`), so the second spawn skips the walk. Give every case its own fresh cache dir (`cache.refresh.test.ts:54-59` `freshCacheDir`) or pin `SESSIONS_REFRESH_INTERVAL_MS=0`.
- **The no-index scanner fallback** (`index.ts:122-126`) produces results without `messageHits`. If `--json` reuses that `try/catch`, the envelope's shape depends on whether the index happened to be readable.
- **`parseArgs` lets the last positional win silently** — `sessions search --json foo bar` searches for `bar`. For a machine surface that is a silent wrong answer; `parseSearchArgs` should reject a second positional.
- **`--json` must write nothing to stderr**, which means suppressing the spinner at `index.ts:116` and the `No sessions found.` line at `:130` — both currently fire before any command-specific branch could intervene.

### Risks

- **The flagship `--no-refresh` criterion cannot pass as the spec designs the change, and I measured it.** Contract criterion (`contract.md:47`) requires `test ! -e "$d/index.db"`. The spec's step 3.1 is "add `noRefresh?: boolean` to the options; short-circuit in `ensureIndexFresh`" — but `getContextPrimer` calls `getDb()` on the line *before* `ensureIndexFresh`, and `getDb()` creates the file. Measured on a fresh temp dir with today's build: `index.db` 4,096 B plus a 235 KB WAL. The fix is to gate the open, not the walk; the spec never mentions `getDb()`.
- **The spec's code sample reintroduces the exact bug its own Failure Modes table says `writeStdoutFully` mitigates.** `writeStdoutFully(...)` returns a `Promise` and the sample does not `await` it before `process.exit(0)`. Measured: 1.2 MB unawaited through a pipe → **65,536 bytes** delivered; awaited → 1,200,000. Every other caller in the repo awaits. At ~1,138 bytes/result (measured over fixtures — real sessions are larger) and a default `limit: 1000`, the truncation begins at ~57 results, and truncated JSON is exactly the "Invalid JSON" impact the table predicts.
- **Three global flags pre-empt the new subcommand, measured.** `index.ts:12` (`--version`/`-v`), `:17` (`--clear-cache`) and `:36` (`--mcp`) use `Bun.argv.includes(...)`. `bun run index.ts search --json -v` → exit 0, stdout `sessions 1.15.3\n`. `search --json --clear-cache` → exit 0, index wiped. The comment at `index.ts:23-25` already documents this class of bug and the fix applied to commands ("Matching anywhere in argv … let a flag VALUE fire a command"); the same fix was never applied to these three. A JSON contract that a query term can break is not a contract.
- **The documented mitigation for the `search`-shadowing failure mode does not work.** The table says `sessions "search"` (quoted, bare) still reaches the picker. Shell quoting is consumed by the shell; `Bun.argv[2]` is `search` with or without quotes. Either pick a real escape hatch (`--`, `--query`, doubling the word) and document that, or accept that the word `search` becomes unsearchable as a bare query.
- **Decision-log contradiction: "acceptance commands run against temp stores and the fixture corpus, never the real ones" is not what the criteria do.** `contract.md:45` and `:46` redirect only `SESSIONS_CACHE_DIR` and `SESSIONS_CLAUDE_DIR`, leaving `SESSIONS_PI_DIR`, `SESSIONS_CODEX_DIR`, `SESSIONS_OPENCODE_DB`, `SESSIONS_MEMORY_DB` and `SESSIONS_HOME` pointed at the operator's real state — measured **166 pi + 303 codex** real transcripts on this machine, all of which get walked and indexed into the temp cache, and any one of them containing "stripe" satisfies `results.length>0` **without the fixture corpus proving anything**. `contract.md:47` redirects only the cache dir, so `context --json` serves the operator's real lessons (read-only — `getMemoryDb()` defaults to `create:false`, verified at `memory.ts:247,254`). The rejected-alternative reason is sound; the criteria it produced do not implement it. Add the remaining `SESSIONS_*` redirections to all three commands.
- **`--json` for `context` cannot be spelled on `SearchOptions`.** `getContextPrimer` takes `ContextOptions` (`cache.ts:1309-1316`), a different interface; and `ensureIndexFresh()` takes no arguments and is called from six sites. Threading `noRefresh` means widening both option types and either parameterizing `ensureIndexFresh` at all six call sites or reading a module-scope flag — the latter is a hidden global under a shared module instance that `bun test` runs in one process, which is precisely how phase 3's `RANKING` mutation risk was described. Prefer the explicit parameter.
- **The envelope creates a CLI/MCP shape divergence for the primer.** `mcp.ts:315` is `JSON.stringify(primer)` — no envelope. After this phase, `sessions context --json` and `get_context_primer` return the same value in two different shapes. The spec's parity requirement covers `search` only, and its own Technical Approach argues the opposite ("two code paths answering the same question is how `get_session_metrics` ended up UTC-wrong on one side only"). Either wrap the MCP primer too (blast radius: every MCP client, plus `context.test.ts:445-446`) or write down that the envelope is a CLI-only concern.
- **Changing `die()` in `cli.ts` to exit 2 changes the bare-query path too.** `die` is module-private and used only by `parseArgs`, so `sessions --nope` would go from exit 1 to exit 2 alongside `sessions search --nope`. ### Edge Cases

- **No CLI found** must be decided *before* the store is opened and before selection: `contract.md:40` asserts `test ! -e "$d/m.db"`, and `proposeLesson` → `getMemoryDb({create:true})` creates the file. That command also overrides only `SESSIONS_MEMORY_DB`, so a selection pass would search (and refresh) the operator's real index.
- **Model output over the write bounds**: `LESSON_MAX_CHARS = 280` / `DETAIL_MAX_CHARS = 600` are enforced in `saveLesson` (`memory.ts:576-585`). A proposal path that skips them stores rows the accept path can never save.
- **Duplicate proposals inside one batch** hit the UNIQUE `content_hash` — handle it like `memory.ts:741-754`, not as an error.
- **Second distill run over the same sessions** → content-hash idempotent, bump `last_seen_at`, insert nothing (that is the spec's "store fills with stale proposals" mitigation, and it works only if the hash is computed the same way: `normalizeText(lesson)\0scope\0repoKey`, `memory.ts:288-294`).
- **Scope of a mined lesson**: `saveLesson` rejects `scope:'repo'` with an empty container (`:586-588`). The container must come from the *mined session's* `cwd` via `resolveRepo(cwd)`, not `process.cwd()` — and that resolve fails when the directory has since been deleted. Decide deliberately: drop, or fall back to `global`.
- **Provenance has no value that means "distilled"**: `Provenance` is `'meta'|'hook'|'env'|'deferred'|'recovered'|'none'` (`types.ts:7`). `'recovered'` currently means "traced by `sessions lessons audit`". Reusing it lies to `lessons.ts:107-111`; adding a sixth value widens the blast radius to `types.ts`, `provenance.ts`, `lessons.ts`. Either way, `verified` must not claim a human said it.
- **A session file that reads back empty** — `readSessionLines(path).length === 0`; skip and count, as `trajectory.ts:346-349` does.
- **Timeout**: `spawnRunner` kills the child but still awaits stdout, so a timeout yields partial output that `extractJsonArray` may half-parse. Fails open, but the warning should say "timed out", not "returned nothing usable".
- **Readonly store** (a `memory.db` from a newer build): `saveLesson` returns a `rejected` result (`:592-596`); `proposeLesson` must do the same rather than throw mid-batch.
- **Quarantined store**: `getMemoryDb({create:true})` moves the corrupt file aside and creates a fresh one, so a distill run into a just-quarantined store silently starts a second store. `warnQuarantined()` (`lessons.ts:139-147`) is the existing way to say so.
- **`--limit` validation**: copy `trajectory.ts:291-296` (`Number.isInteger(v) && v > 0` or `die`), then clamp to 50 — `--limit 0` and `--limit -1` must not reach the clamp as "min".
- **`--days` against the eval corpus is time-bombed**: fixture timestamps are frozen at `2026-04-06` … `2026-04-29`; today is `2026-07-27`. `--days 1 → none` is safe forever, but any "`--days N` selects them" assertion flips to selecting nothing as the clock advances. - **A `--query`-less run scoped into a junk root** re-admits automated sessions (`cache.ts:794`, `isJunkScope`) — the one hole in "selection goes through `searchSessions`, which excludes junk cwds".

### Risks

- **The spec's central premise understates the work by 2×, and I measured it.** The spec and `contract.md:19` both say the corpus "is insensitive to two of the four" mutants. Measured against the recall ratchet, **all four survive** — no `RECALL_FLOOR` entry is violated by any mutant, and not one expected-answer rank degrades. Expect four survivors on the first harness run, not two, and budget the fixture work accordingly. This is a decision-log contradiction: the entry _"Retrieval quality becomes a real track, with corpus growth as its prerequisite"_ and the entry _"The corpus is done when four named mutants are killed"_ both rest on the two-of-four premise; the premise is wrong in the direction that makes the phase *more* necessary, so the decisions stand, but the effort estimate does not.
- **Two mutants "die" today for the wrong reason, and the spec's `anyFloorViolated` will believe them.** `USER_HIT_BOOST → 1.0` exceeds two payload ceilings (exact-error-string 5847 vs 5826, command 4393 vs 4352) and `finalRank → best-of` exceeds one (multi-word 6592 vs 6506) — deltas of 21, 41 and 86 characters, incidental serialization wobble with no ranking meaning. - **The killing oracle is one-sided and two mutants move the metric the wrong way.** `bm25`-flat and `USER_HIT_BOOST → 1.0` both promote `nl-webhook-signature-fix` from rank 2 to rank 1, lifting multi-word recall@1 from 0.80 to 1.00. New fixtures for these two mutants must create a case where the tuned value is strictly better, not merely different — and it is worth asking whether `nl-webhook-signature-fix`'s recorded miss is itself a mis-tuning rather than a distractor working as designed.

### Conventions

- **Naming**: flat `src/*.ts`, lowercase, dot-suffixed test files next to their subject (`memory.ts` → `memory.test.ts`, `memory.survival.test.ts`, `memory.export.test.ts`). Fixtures in `src/__fixtures__/`. Module-private helpers are plain `function`; the exported surface is explicit. Constants are SCREAMING_SNAKE at module scope (`SCHEMA_VERSION`, `LESSON_MAX_CHARS`, `SAME_LESSON_JACCARD`).
- **Imports**: relative with no extension (`./paths`, `../cache`), no barrels. `verbatimModuleSyntax` is on, so type-only imports must be written `import type`. `node:` prefix on all builtins (`node:fs`, `node:path`, `node:os`). `bun:sqlite` / `bun:test` for Bun builtins. One in-file `require('node:fs')` exists at `src/cache.ts:84,198,290` — legacy, not the pattern to copy.
- **Error handling**: swallow-and-continue for anything disposable (`try {} catch {}` around unlinks and readdirs); throw only where the caller can act. Failures the user must know about are written to `process.stderr` and never to stdout (stdout is a data channel — see `src/stdout.ts`). `isCorruption()` exists twice on purpose (`src/cache.ts:206`, `src/memory.ts:162`) with opposite responses — delete-and-rebuild vs quarantine-and-keep.
- **Types**: `interface` for object shapes, `type` for unions/aliases; `LessonRow` mirrors the SQL columns in snake_case while the exported projection (`ExportedLesson`) is camelCase. `db.query<Row, Params>()` is always parameterized. `strict` + `noUncheckedIndexedAccess` are on, so indexed access needs `!` or a guard.
- **Testing**: `bun:test` with `describe`/`test`/`expect`; `spyOn(process.stderr, 'write').mockImplementation(...)` is the only mocking idiom in the repo (10 uses) — there is no `mock.module` anywhere. Hermetic files use `mkdtempSync(join(tmpdir(), 'sessions-<area>-'))` at module scope, set env, then `await import(...)` the subject. Real subprocesses are preferred over simulated races. Test prose is explanatory (a `describe` name is a sentence).
- **Formatting**: `.oxfmtrc.json` — single quotes, semicolons, trailing commas everywhere, 2-space indent, printWidth 120. `oxlint` runs with an empty rule set, so `bun run format:check` is the real style gate. `ignorePatterns` covers `dist/`, `node_modules/`, `CHANGELOG.md`, `.github/`, `plugin/*/plugin.json`, `docs/ideation/` — note `docs/` generally is **not** ignored.

### Risks

- **`PRAGMA data_version` cannot order the snapshots as the spec uses it — verified, two separate defects.** (1) The column is named `data_version`, so the spec's `db.query<{n:number}>('PRAGMA data_version').get()?.n ?? 0` evaluates to `0` on every call and the `gen >= readSnapshotGeneration()` check silently degrades to `0 >= 0` — always true, guard absent. (2) SQLite does not increment `data_version` for changes made on the *querying* connection; measured directly: after this connection's own `INSERT` it stayed `1`, and only a second connection's commit moved it to `2`. So the writer that just committed sees a counter that does not reflect its own write, which is exactly the ordering the contract criterion depends on ("the surviving snapshot contains the LATEST committed rows"). A monotonic counter bumped inside the same transaction as the lesson write (or `MAX(id)`+`MAX(last_seen_at)` read post-commit) is needed instead. Do not ship the spec's snippet verbatim.
- **"The lock is an atomic `mkdir` (the repo's existing idiom)" is false — there is no such idiom.** Every `mkdirSync` in the tree passes `{recursive: true}`, which never throws `EEXIST` and therefore cannot function as a lock. The repo's real cross-process idiom is atomic tmp-write + `renameSync` (`src/report/pricing-cache.ts:63-74`). The mkdir lock must be written from scratch, including the dead-PID reaping the spec asks for, and a leftover lock *directory* beside `memory.db` will break `src/memory.test.ts:54`, whose `beforeEach` does `for (const f of readdirSync(fixtureRoot)) unlinkSync(...)` — `unlinkSync` on a directory throws `EPERM`/`EISDIR`.
- **`src/memory.survival.test.ts:84-100` deletes all eight `SESSIONS_*` vars in `afterAll`.** This is the live hermeticity hole and it is in-scope even though the spec's Modified Files table omits it: after that file runs, any later test file in the same process resolves the **real** `~/.local/share/sessions/memory.db` and `~/.cache/sessions/index.db`. Once `assertNotRealStore` lands, this teardown turns the suite red rather than silently corrupting the store — good, but the builder must restore the preload's values instead of deleting. Same class, lower stakes: `src/report/pricing-cache.test.ts:16` and `src/report/extract.test.ts:76-78` also `delete` overrides.
- **A new `meta` table will survive a `SCHEMA_VERSION` bump unless it is added to the drop list at `src/cache.ts:120-123`.** That list is hardcoded, not schema-driven. Leave `meta` out of it and a version bump empties every index table while `last_refresh_ms` still reads "just walked" — `ensureIndexFresh` then skips the rebuild and serves an empty index for the length of the refresh interval (longer if `SESSIONS_REFRESH_INTERVAL_MS` is raised).
- **`--purge-lessons` stops purging.** `purgeLessons()` (`src/memory.ts:979-989`) removes only `memory.db` and its journal sidecars. After this phase, `memory.db.snapshot` and `lessons.jsonl` — a byte-complete copy and a plaintext dump of the same lessons — survive a purge the user was warned costs them "N lessons that nothing can regenerate" (`src/setup.ts:344`). `src/memory.survival.test.ts:211` still passes because it only asserts `memory.db` is gone, so nothing catches this. Extend `purgeLessons` and its test.
- **Both seams the spec's experiments need are module-private.** `discoverFiles` (`src/cache.ts:231`) is not exported and cannot be stubbed — there is no `mock.module` usage in the repo, and it internally swallows `readdir` failures (`:241, :257`), so it is hard to make throw at all. `ensureIndexFresh` (`:541`) is not exported either, so `src/__fixtures__/concurrent-refresh.ts` cannot call it directly; the child must go through an exported consumer (`searchSessions`, `getIndexDb`, `getContextPrimer`) or the builder must add an explicit test seam. Also note `refreshIndex` does **not** consult the marker in the spec's design — only `ensureIndexFresh` does — so a fixture calling `refreshIndex` will always walk.
- **The marker makes `ensureIndexFresh` return a stale `{total: 0, updated: 0}`.** A fresh process that skips the walk on a marker hit returns the module-initial `_lastRefreshResult` (`src/cache.ts:68`), i.e. "0 sessions indexed". No current consumer reads that value (`src/eval/run.ts:181` calls `refreshIndex` directly), but any future "indexed N" display would be lied to. Also, `closeDb()` (`:102`) resets `_lastRefreshAt = 0`, which wipes an in-process failure backoff — the backoff test must not call `closeDb` between attempts.
- **`_lastRefreshAt = Date.now() - refreshIntervalMs() + FAILURE_BACKOFF_MS` back-dates into the future when the backoff exceeds the interval.** With the 5s default and a 30s backoff, `_lastRefreshAt` lands 25s ahead of now. The comparison still behaves, but it also overrides an explicit `SESSIONS_REFRESH_INTERVAL_MS=0` ("always refresh") with a 30s lockout, and a future-dated `_lastRefreshAt` is the same shape as the clock-skew failure mode the spec's own table says to treat as expired.
- **Three paths bypass `paths.ts` and the preload cannot reach them.** `src/opencode.ts:17` resolves `SESSIONS_OPENCODE_DB` against a raw `homedir()`, not `getHome()` — so with only the spec's five vars set, every index refresh under test reads the developer's real OpenCode database (this is why `src/cache.search.test.ts:22` and `src/memory.survival.test.ts:29` set it by hand). `src/hooks.ts:36` does the same with `SESSIONS_CLAUDE_CONFIG_DIR`, and that one is a *write* path into `~/.claude/settings.json`. `src/scanner.ts:12-15` freezes `homedir()` at import and honors no override at all; it is reachable (`index.ts:5`). Reads cannot fail the contract's byte-identical check, but the hooks write can — add `SESSIONS_OPENCODE_DB`, `SESSIONS_CLAUDE_CONFIG_DIR`, and the three source-root vars to the preload.
- **The guard only covers DB openers, so a scrubbed-env child that does anything else is still unprotected**, by design. Related: `src/mcp.test.ts:376` spawns the real MCP server with no `env` at all (inheriting, therefore safe under the preload), while `:488`, `:537`, `:598` and `src/trajectory.test.ts:162` spawn with `{...process.env, <override>}` — also safe. The spec's `env: {}` experiment is synthetic; on macOS a child with a truly empty environment still starts because `process.execPath` is absolute, but keep `stderr: 'pipe'` and assert on the message, not just the exit code. _(Phase 2 correction: the parenthetical about `mcp.test.ts:376` is wrong on the mechanism — measured on Bun 1.3.14, a child spawned with no `env` does **not** see runtime `process.env` mutations, so it has neither the redirection nor `SESSIONS_TEST`. See the Phase 2 Risks.)_
